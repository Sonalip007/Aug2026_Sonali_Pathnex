Step 1 — Pod is created :

The Deployment creates a ReplicaSet, and the ReplicaSet creates the Pod.

you might see nginx-7d8f9c6d4b-x2abc. At this point kubernetes know "I need this pod to be run" but it hasn't necessarily decided which node
should run it yet. so pod goes to pending statefulset

Step 2- Pending :
AT this stage if you do kubectl get pods you can see 
NAME                     READY   STATUS    RESTARTS   AGE
nginx-7d8f9c6d4b-x2abc   0/1     Pending   0          2s

Kubernetes is figuring out:
Which node has enough CPU?
Which node has enough memory?
Are there scheduling restrictions?
Are there taints/tolerations?
Are node selectors/affinity rules satisfied?
Does the Pod need particular resources?
This is mainly the Scheduler's job.

Now based on above points scheduler chooses a node. Scheduler says e.g node 2 is suitable put the pod there. Pod is scheduled to Node-2.

Step 3: container creating
Kubernetes starts preparing the Pod
Now Node-2's kubelet takes responsibility.
Think kublet as The manager on each Kubernetes node who makes sure the Pods assigned to that node are actually running.
Now it start preparing everything required

Q.when you see CrashLoopBackOff : Suppose your application starts and immediately crashes
It means "Your container keeps crashing, so I'm waiting longer between restart attempts."

Q.When you see ImagePullBackOff : Happens when image can't be pulled
 
Q.Difference between ImagePullBackOff &CrashLoopBackOff
ImagePullBackOff : The container couldn't even start because the image couldn't be pulled.
CrashLoopBackOff : The container started but keeps crashing.

Q. What is SIGTERM (signal termination)
When Kubernetes wants the container to stop, the container runtime sends a termination signal. tells application "Please shut down gracefully."
your application termination flow will be: 
Stop accepting new requests
       ↓
Finish existing requests
       ↓
Close database connections
       ↓
Save important state
       ↓
Exit

If it doesn't terminate within the grace period, Kubernetes can force termination.

Q. Node affinity : Giving the Scheduler rules about where you want a Pod to run.
Normally, the Scheduler looks at available resources and other constraints
With affinity, you can tell it: I prefer this type of node

There are two types of affinity : Node affinity & Pod affinity

1. Node Affinity : it says I want my Pod to run on a particular type of Node
Suppose your nodes have labels:
Node-1
  disk=ssd

Node-2
  disk=hdd

Node-3
  disk=ssd
 
 here you can tell kubernetes : "Put my database Pod on a node where disk=ssd."
 
 affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
        - matchExpressions:
            - key: disk
              operator: In
              values:
                - ssd

Note : there are two terms : 1.requiredDuringSchedulingIgnoredDuringExecution  2. preferredDuringSchedulingIgnoredDuringExecution
required : if No node has disk=ssd pods wont be scheduled 
preffered : means saying "I would like this, but it's not mandatory." in this case if No node has disk=ssd pods it will schedule on other node

2. Pod Affinity : it says, I want my Pod to run near another Pod
for e.g you want to run Frontend pod near Backend pod, The Scheduler tries to place them according to the affinity rule.

3. we have concept called as anti affinity : 
Way of saying "Don't put my Pod near another Pod."
Suppose you have 3 pods running at one node. now suppose that node dies, you will loose all pods at once.
Anti affinity spreads pods


QA. What is taint & toleration :
taints are on nodes, and tolerations are on pods.

e.g Let’s say you have a node with very expensive GPU hardware, and you want only special pods to run there. You add a taint on that node
kubectl taint nodes gpu-node key=gpu:NoSchedule 
That means: "No pod is allowed here unless it tolerates key=gpu." (toleration chya at je lihilay te tolerate hot asel tarch allowed honar)

Q. 3 Taint effects
NoSchedule  : Don't schedule new Pods here unless they tolerate the taint
PreferNoSchedule : The Scheduler tries to avoid it, but may use it if necessary
NoExecute : Don't schedule new Pods here, and Pods already running here may be evicted if they don't tolerate the taint.
